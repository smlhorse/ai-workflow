# bnworkflow:spec

## 核心心法

**規格是描述，不是步驟** — spec 回答「系統長什麼樣 / 元件怎麼運作」。實作步驟是 plan 的事。spec 寫成步驟清單 → 整份重寫。

**元件 ID 是錨點** — 每個 UI 元件配一個唯一 ID（如 `cmp-order-list`、`btn-mark-inbound`），A-E 5 表都用此 ID 串接。沒 ID 的元件不能寫進 spec。

**失敗情境與 happy path 同等重要** — B（撈不到資料）、C（前置條件不滿足）、D（API 失敗）每項都要有對應處理。只寫成功路徑 → 整份打回。

## 觸發判斷

**走 spec 的訊號**（任一出現）：
- 任務提到「畫面 / 頁面 / 介面 / 元件 / 按鈕 / 列表 / 表單 / 互動」
- 新增或修改任何 UI 元件
- 改變使用者操作流程

**不走 spec**：純 API / DB / 演算法 / 重構 / 修 bug 且不影響 UI；設定檔、文件、CI/CD。

**模糊不自己猜**：任務描述同時可能是 UI 或後端（如「優化訂單功能」）→ 停下問 user，不自行判定走哪條。

## 5 表 schema（產出位置：`tmp/spec.md`）

開頭先寫業務目標段（PM 負責，純文字）：
- **業務目標**：對齊 anchor 的核心目的
- **優先序**：哪些元件先做、哪些後做

接著 5 張表：

### A. VISUAL — 外觀 / 位置
| 區塊名稱 | 元件 ID | 截圖 | 在畫面哪 | 視覺類型 | 預設狀態 |

### B. DATA — 資料來源 / 撈出條件
| 元件 ID | 資料來源 | 撈取時機 | 撈取條件 | 顯示欄位 | 排序 / 預設 |

### C. INTERACTION — 行為 / 事件
| 元件 ID | 觸發事件 | 前置條件 | 操作員看到什麼 |

### D. FLOW — 後續流程 / 影響
| 元件 ID | 系統做什麼 | API call | DB 變更 | 影響哪些畫面 / 流程 | 失敗處理 |

### E. STATUS — 規格狀態 / 異動
| 元件 ID | 規格狀態 | 最後更新 | TODO 連結 |

## 不做的事

- 不寫實作步驟、技術選型、檔案結構（plan 與架構師職責）
- 不在 A-D 表留空欄位；不知道就寫「待 SA 釐清」並列入待確認
- 不手動填 E.STATUS 的「最後更新」欄位（由 git log 維護，欄位寫 `—`）
- 不只寫 happy path：B/C/D 必含失敗、空值、權限不足、網路失敗等對應處理
- 沒元件 ID 的元件不寫進表
- 不重複描述同一元件在不同表的資訊（5 表用 ID 串接，不冗餘）
- 不為單一元件畫獨立區段；同類元件併入同一張表的多列

## 角色分工

- **PM**：寫開頭業務目標 + 優先序段（純文字）
- **資深 SA**：主寫 A-D 四張表，負責邊界條件覆蓋
- **UI/UX**：協同 SA 寫 A.VISUAL 和 C.INTERACTION
- **三大架構師**：透過 `bnworkflow:review` 審查（不主寫）
- **E.STATUS**：「最後更新」欄位 git log 維護

## 自主決策邊界

**自己決定**：元件 ID 命名（依現有命名慣例）、5 表內欄位寫法、是否拆多張子表（同類元件超過 10 列可拆）。

**停下來等確認**：
- 任務描述 UI / 後端模糊 → 問 user 走哪條
- 業務目標不明確 → 回報 PM，不自行詮釋
- 任一表出現「待 SA 釐清」項目超過 3 個 → 停下回報，先收斂需求再續寫

## 工作流

讀 anchor → 確認走 spec（依觸發判斷）→ PM 寫業務目標段 → SA 主寫 A-D（UI/UX 協同 A、C）→ 自檢 5 表 ID 一致性與失敗情境覆蓋 → 呼叫 `bnworkflow:review` 多角色審查 → 等 ack → 交棒 `bnworkflow:plan` 拆步驟（plan 步驟必須對齊 spec 元件 ID）
