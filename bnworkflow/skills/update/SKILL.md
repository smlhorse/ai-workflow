# bnworkflow:update

## 用法

```
/bnworkflow:update        ← 在已跑過 init 的專案執行
```

plugin 升級後，新規則與新產物不會自己出現在既有專案（規則檔與角色檔是當初複製的複本）。這個指令負責把落差補上。

## 檢查範圍

框架會產出的東西都查一遍：專案 `CLAUDE.md` 的章節、`.claude/CLAUDE.md` 的規則條目、`.claude/roles.md` 的角色、`.claude/settings.json`、`.gitignore` 該有的行、`.team/` 團隊記憶（沒建過→問要不要建並選成員；已建→查成員卡與工作管理檔的欄位是否比底稿少，含新增的溝通與洞察、指派語句等節）。

## 核心心法

**比對，不覆寫** — 專案端全是複本，user 可能改過。只找「plugin 有、專案沒有」的東西；專案自己多出來或改寫過的一律保留，不當成錯誤、不回退。

**逐條比，不整份換** — 規則檔以「條」為單位（比條目標題）、角色檔以「角色」為單位、成員卡以「欄位」為單位。整份覆蓋會把在地調整洗掉，這是最貴的錯。

**差異先列完，user 勾了才動手** — 一次列出所有落差與各自用途，等 user 決定補哪些。未勾選前不寫入任何檔案。

**沒建過的不算缺陷，但一定要列出來** — 團隊記憶、可選產物目錄都是選用。沒有的照樣列進差異清單並說明用途，user 說要就建、說不要就跳過；不主動催，也不因為「他沒有」就當作不需要而略過不提。

**內容衝突交給 user** — 同一條規則專案版與 plugin 版寫法不同（user 改過或框架改版），列出兩邊差異讓 user 選，不自行合併也不自行判斷誰新。

**成員卡只補欄位** — 底稿新增的欄位補成空欄讓 user 填，不動已寫的姓名、人設與職能調整。

## 不做的事

- 不刪除專案自己多出來的規則、角色或檔案
- 不順手整理與框架無關的內容
- 不用「應該要有」的理由自行補齊未勾選項目

## 自主決策邊界

**自己決定**：比對方式、差異呈現順序。

**停下來問**：每一項要不要補、內容衝突取哪一版。
