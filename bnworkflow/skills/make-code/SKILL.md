# bnworkflow:make-code

## 核心心法

**Scope 鎖定** — diff 必須能對照 anchor，每個改動都要能說出對應的需求。無法對應的改動，若涉及架構或系統邏輯，需取得 anchor 確認才動手；其餘小改動移至下一個任務單獨處理。

**Design Fidelity** — 改任何現有功能前，必須先讀原始碼確認現有設計。不得用「我覺得合理」的替代品取代，不重新發明已有命名。

**完成 ≠ 語法正確** — 完成的最低門檻是自驗通過：程式碼修改必須 build 通過且業務邏輯正確、API 修改必須正向測試 + 至少一個邊界條件、文件修改必須結構正確且無過程性資訊殘留。

## 不做的事

- 無法對照 anchor 的改動：涉及架構或系統邏輯 → 停下確認；明顯必要的小修正（typo、missing import）→ 做完告知即可
- 不異動工作目錄以外的 repo 
- 不用「應該沒問題」代替實際驗證
- 工具回傳非零退出碼或警告 → 停下診斷根因，不跳過繼續
- 有中間產物的步驟（build artifact、migration、生成檔案）完成後確認產物存在，才繼續下一步
- 發現實作與規格不符 → 停下告知，等指示，不自行詮釋哪個對
- 不分批發問，完整思考後一次列完所有疑問
- 有疑問前先查對話上下文與規格文件；同一對話中 user 已回答的問題不重問

## 自主決策邊界

**自己決定，做完告知**：codebase 已有相同模式、單一檔案小改動、命名格式。

**停下來等確認**：
- 操作永久不可逆或產生額外費用
- 業務規則不確定（BLOCKED：直接停，輸出 `[BLOCKED]` + 具體問題，不繼續執行）
- 規格有矛盾
- 需動指定範圍外的檔案
- UAT／PROD 寫入

## 完成後

```
做了什麼：{改動檔案與業務說明}
沒做什麼：{及原因}
假設：{讓 user 確認的假設，無則寫「無」}
自驗結果：{build / 測試 / 邊界條件結果}
文字來源核對：{列出本次所有欄位名 + 提醒/錯誤/提示文字，逐一標出規格來源位置；無來源者列待確認。本次無新增文字則寫「無」}
需你決策：{若有，否則寫「無」}
```

**改動呈現規則：**
- diff ≤ 10 行：直接在回應裡附區塊式 diff（含上下各 3 行上下文與行號）
- diff > 10 行：回應只列摘要（檔案:行號 + 一行說明），完整內容寫進 `tmp/report.md`
- user 明確要求細節：不論行數，寫進 `tmp/report.md` 並告知路徑
