# bnworkflow:make-testplan

## 核心心法

**Shift-left** — 規格定案後不等工程做完，與工程軌**並行**寫測試計畫。測試不是做後補的尾巴，是規格的另一面。

**從規格寫測試逼出規格漏洞** — 把每條規格翻成測試案例的當下，會撞出規格沒說清的失敗情境、空值、權限、邊界＝一次早期 spec review。撞到漏洞 → 回報，不自行腦補規格。

**覆蓋 happy path 之外** — 每條規則都要有失敗、空值、權限、邊界的對應案例。只寫 happy path 的測試計畫等於沒寫。

## 產出

測試計畫落 `docs/qa/{sprint}_測試計畫_v{N}.md`（版本化；spec 變更 → v+1，舊版保留；專案 CLAUDE.md 可覆寫路徑/檔名）。每條測試案例標明對應的規格條目。

**兩軌案例**：
- **功能測試**：每條規則的 happy path＋失敗/空值/權限/邊界
- **非功能測試（有 SLA/容量要求才寫）**：效能/負載/壓測/容量案例，對應 SDD 的容量規劃與 SLA；標明目標值與量測方式

## 不做的事

- 不只寫 happy path → 失敗/空值/權限/邊界各有對應案例
- 不寫實作、不寫怎麼修 → 只描述「驗什麼、期望什麼」
- 測試案例無對應規格條目 → 列待確認，不自編需求
- 撞到規格漏洞 → 停下回報，不自行詮釋規格
- 有效能/容量 SLA 卻只寫功能測試 → 不完整，須補非功能案例
- 有 WBS（`docs/wbs/`）時本關完成必更新對應 WBS 節點狀態（make-testplan 完＝已產出，無獨立 review 關卡，由 verify 執行）；不更新＝不算完成
- 無 WBS/Issue 時不腦補，先查 anchor，缺資訊回報

## 自主決策邊界

**自己決定**：測試案例結構、case ID 命名、邊界情境的列舉。

**停下來問**：規格本身有矛盾或缺口、驗收標準不明、規格未定案。

## 角色

SQA 主寫，UI/UX 協同（補 UI 測試情境）。與工程軌（make-design → make-plan → make-code）**並行**。計畫寫成後交棒 `bnworkflow:verify`——verify 執行此計畫產生測試紀錄。
