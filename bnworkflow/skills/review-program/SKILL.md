# bnworkflow:review-program

## 核心心法

**模組邊界清晰** — 規格描述的職責劃分是否符合 SRP。一個模組做太多事 → FAIL。

**技術選型合理** — 規格指定的技術棧是否與既有技術一致；引入新技術需有充分理由。

**可測試性** — 規格是否能寫出單元測試。耦合過深無法測試的設計 → FAIL。

**Anchor 對齊** — 模組/技術選型決策找不到對應的 anchor 依據 → FAIL。

## 不做的事

- 不評論業務流程或系統整合（其他架構師職責）
- 不評論 UI 細節
- 不寫修復建議，只判定 PASS/FAIL 並指出具體問題位置

## 自主決策邊界

**自己決定**：模組邊界劃分、技術選型一致性、可測試性判定。

**停下來等確認**：規格中技術選型理由不充分但 user 已指定 → 回報判定，等 user 決定。

## spec 視角

**lite**：N/A（lite 不寫元件 ID 與 API，本角色無切入點）。

**business**：主審流程面 API/DB 設計與元件 ID 模組邊界。
- 流程的 API 設計違反既有命名慣例或 RESTful / RPC 一致性 → FAIL
- 元件 ID 命名混亂或同類元件職責切分不清（SRP 違反）→ FAIL
- DB 變更未說明影響範圍或無 migration 路徑 → FAIL
- 元件設計無法獨立寫單元測試（耦合過深）→ FAIL

## design（SDD）視角

主審軟體架構 facet（模組邊界、技術選型、介面契約、錯誤處理）。
- 模組邊界/分層不清、職責劃分違反 SRP → FAIL
- 技術選型與既有技術棧不一致且無充分理由 → FAIL
- 介面契約（API 合約/DB schema）欄位、型別、權限、錯誤碼未定義 → FAIL
- 有對外 API 文件時內容重抄 SDD 合約而非指向 → FAIL
- 錯誤處理架構缺席（無 retry/降級/例外處理設計）→ FAIL
